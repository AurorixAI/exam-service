# exam-service

Сервис управления экзаменами. Учитель создаёт экзамен, генерирует варианты через Gemini AI, студенты проходят — сервис сохраняет ответы и считает результаты.

- **Port**: 8003
- **DB**: `algo_exam` (PostgreSQL 15)
- **Cache**: Redis (кэш шаблонов, TTL 1ч)
- **Framework**: FastAPI + SQLAlchemy ORM + Alembic
- **Main file**: `src/main.py`

### Публичный вход ученика: защита от перебора (ROADMAP #33)

`POST /exams/by-code/{code}/check-student` и `/start` возвращают имя ученика при совпадении ID/ФИО, поэтому по коду экзамена
нельзя перебирать ID и собирать состав группы. Что сделано:

- Лимиты по паре (код экзамена, IP клиента) и по коду; IP — только `X-Real-IP` (его ставит nginx; `X-Forwarded-For` не доверяем),
  IPv6 считается по /64. Счётчики — Redis (общие для воркеров), без Redis — память процесса с одним предупреждением в лог.
- Строго считаются **различные неудачные вводы** (не найден / неоднозначно / имя не от этого ID): 30 в минуту и 150 в час на (код, IP);
  повторный ввод того же неверного ID или имени считается один раз. Неудача резервируется атомарно при допуске запроса (Lua) и возвращается,
  если ученик найден или запрос закончился не поиском (410, 503), поэтому параллельные запросы не превышают бюджет.
  Все попытки (check + start) — только защита от флуда: 120 в минуту и 400 в час на (код, IP). Класс из 30 человек за одним NAT проходит целиком.
- Предохранитель по коду: если у кода набралось 200 различных неудач за час, отказ получает только IP, у которого уже >= 30 различных неудач
  и больше половины его *завершённых поисков* неудачны (различные неудачные вводы против различных найденных учеников; отказанные, пустые
  и оборвавшиеся запросы ничего не завершают, поэтому игнорировать Retry-After не помогает). Остальные (класс с парой опечаток) входят.
- Набранные ID/имена в Redis хранятся только как HMAC-хеш; ключ — `ENTRY_LIMIT_SECRET`, иначе производный от `INTERNAL_SERVICE_TOKEN`,
  иначе (разработка) случайный на процесс с предупреждением в логе.
- Ответ при превышении: `429`, заголовок `Retry-After` (максимум по всем превышенным окнам), текст «Слишком много попыток. Подождите минуту и попробуйте снова.»
  (при ожидании больше полутора минут — «Подождите N мин ...»).
- `POST /exams/{id}/entry-limits/reset` — преподаватель группы сбрасывает все ограничения входа своего экзамена (только пока экзамен в лобби/идёт).
  Ключи содержат номер эпохи кода; сброс увеличивает номер, старые ключи больше не читаются и истекают сами.
- Любой отказ (нет такого ID, чужое имя к ID, однофамильцы, пустая группа) — один и тот же текст «Ученик не найден в этой группе — проверьте имя или ID»;
  причины auth-service до ученика не доходят. Имя возвращается только при точном однозначном совпадении (форма ответа не менялась).

### Привязка экзамена к занятию (ROADMAP #88)

`publish`, `assign` (с `publish`), `open-lobby` и подготовка печатного комплекта отказывают с `409` «Занятие уже прошло или отменено — выберите другое»,
если занятие завершено или отменено, или его день прошёл, или сегодня плановый конец уже наступил, а занятие не идёт
(`in_progress` проходит даже после планового конца; будущие дни проходят). Время — Asia/Tashkent; правило повторяет `isLessonBindable` во фронтенде.
Статус занятия берётся у auth-service (`/auth/org/groups/{id}/attendance`); если он недоступен — `503`, привязка не выполняется.

### Класс пишет один экзамен: нет зависаний (ROADMAP #95)

Раньше `progress`/`submit`/`start` были `async def` на **блокирующей** сессии SQLAlchemy: запрос, ждущий блокировку строки
`generated_exams`, останавливал event loop воркера, а запрос, державший эту блокировку, стоял на `await` к auth-service внутри
открытой транзакции и не мог продолжить. Два воркера — и сервис не отвечал, включая `/health`. Правила теперь такие:

* Обработчик без `await` — обычный `def` (FastAPI гонит его в пул потоков). Обработчик, которому нужен auth-service
  (`by-code`, `check-student`, `start`), делает три шага: БД в потоке (`run_in_threadpool`, транзакция закрыта) → вызов
  auth-service без транзакции и без соединения → БД в потоке, одна короткая транзакция. Тест `tests/test_concurrency_safety.py`
  не даёт вернуть `await` после блокировки и транзакцию через сетевой вызов.
* Сохранение ответов и сдача блокируют **строку попытки ученика** (`exam_sessions … FOR UPDATE`), а не общую строку экзамена;
  таймер, который ещё не истёк, не требует никакой блокировки экзамена. Эксклюзивную блокировку строки экзамена берёт только
  тот, кто его закрывает (по таймеру или учитель), порядок везде «экзамен → попытки». `start` берёт общую (`FOR SHARE`).
* Сервер БД ограничивает каждое соединение: `lock_timeout` 5 с, `statement_timeout` 15 с, `idle_in_transaction_session_timeout` 30 с.
  Истёкший таймаут — это `503` + `Retry-After: 2` и русский текст; ничего не записано, повтор безопасен (повторное сохранение
  то же, повторная сдача — `400 «Экзамен уже сдан»`, оценка одна).
* `/health/live` отвечает самим event loop; `/health` проверяет БД/Redis в отдельных потоках и отвечает не дольше 4 с.

Нагрузочный прогон на настоящем Postgres + Redis + `uvicorn --workers 2` с auth-заглушкой (50–200 мс):
`python -m tests.load.class_load --students 60 --pg … --redis …`; тот же набор как pytest — `tests/test_class_load_pg.py`
(пропускается без `EXAM_LOAD_PG_URL` / `EXAM_LOAD_REDIS_URL`, см. docstring).
